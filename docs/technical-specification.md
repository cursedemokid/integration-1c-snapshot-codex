# Техническое задание IntegrationOneS

## 1. Назначение

IntegrationOneS сверяет документы и остатки между базой 1С «Управление торговлей»
и бухгалтерскими базами БУХ2019 и БУХ2026. Сервис получает данные по HTTP,
нормализует их, сопоставляет склады и документы и возвращает один XLSX с результатами
сверки и перечнем необходимых действий.

Текущая редакция учитывает расшифровку встречи 11.09.2026 и переданную после неё
таблицу соответствия документов. Пользовательский XLSX показывает количественные
расхождения остатков, а затем список значимых документов товарного движения.

## 2. Источники данных

Сервис использует три независимых источника:

- УТ: движения и остатки `data1C/stocksturnover`, склады `data1C/warehouse`;
- БУХ2019: движения и остатки `dataBUH2019/stocksondate`, склады `dataBUH2019/warehouse`;
- БУХ2026: движения и остатки `dataBUH2026/stocksondate`, склады `dataBUH2026/warehouse`.

Ответы 1С имеют вид `{"code": 200, "data": [...]}`. Параметры подключения и
учётные данные читаются только из локального `.env` и не включаются в Git или сборку.

## 3. Сопоставление складов

- Коды складов разных баз не считаются одинаковыми автоматически.
- Склад УТ связывается с бухгалтерией по полю `СкладБухгалтерия`.
- Значение связи сравнивается с названием склада отдельно в БУХ2019 и БУХ2026.
- При сравнении нормализуются Unicode, регистр и лишние пробелы.
- Несколько физических складов УТ с одной связью образуют один логический склад.
- Автоматическая связь используется только при однозначном результате во всех БУХ.
- Подтверждённые исключения допускаются через `ONEC_WAREHOUSE_MAPPINGS_JSON`.
- Пустые, отсутствующие, неоднозначные и конфликтующие связи не используются для
  фильтрованной сверки и отражаются в диагностике `GET /warehouses`.

## 4. API

### 4.1. Служебные методы

- `GET /health` возвращает состояние сервиса.
- `GET /warehouses` возвращает справочники баз, логические склады и диагностику связей.
- `GET /` возвращает web-интерфейс.

### 4.2. Формирование отчёта

`POST /reconcile` принимает прежний JSON-контракт:

```json
{
  "start_date": "DemoPhone",
  "end_date": "DemoPhone",
  "warehouses": ["upr000234_bd000001"]
}
```

- Обе даты включаются в период.
- `warehouses` содержит логические ID из `GET /warehouses`.
- Неизвестный или устаревший ID возвращает HTTP 422 до загрузки движений.
- Для одного физического склада разрешён серверный фильтр `warehouse`.
- Для группы складов база выгружается один раз, затем строки фильтруются локально.
- Внутренние перемещения внутри одной логической группы не считаются пропущенными.
- Для этого используется готовое соответствие складов из выгрузки; дополнительные
  запросы свойств складов не выполняются.
- Бухгалтерские базы проверяются независимо; ошибка одной базы не скрывает результат другой.

Успешный ответ сохраняет `Content-Type` XLSX и имя:

Демо Пользователь
Список_документов_для_исправления_YYYY-MM-DD_YYYY-MM-DD.xlsx
```

## 5. Сверка документов

В автоматическую сверку входят только документы, меняющие количество товара.
Предварительная матрица соответствий:

| Документ УТ | Документ БУХ/НБ | Состояние правила |
| --- | --- | --- |
| Перемещение, Передача товаров филиалу (ПТФ) | Перемещение | активно |
| Поступление товаров и услуг | Поступление товаров и услуг | активно |
| Реализация товаров и услуг | Реализация товаров и услуг | активно |
| Оприходование | Оприходование | активно |
| Списание товаров | Списание товаров | активно |
| Комплектация номенклатуры | Комплектация номенклатуры | ожидается признак разновидности из 1С |
| Требование-накладная | Списание или Безвозмездная передача | ожидается признак разновидности из 1С |

`Поступление дополнительных расходов`, `Заказ покупателя`, неизвестные и остальные
неподтверждённые типы исключаются. Комплектации, требования-накладные и безвозмездные
передачи до согласования разновидности не создают автоматических рекомендаций. Их число
показывается на листе `Итоги` как ожидающее правила. Окончательный allowlist заменяется
на утверждённый заказчиком список без изменения HTTP-контракта.

Флаги управленческого, бухгалтерского и налогового учёта не используются для исключения
документов: отсутствие флага может быть ошибкой пользователя.

Документы сопоставляются последовательно:

1. по идентификатору исходного документа, если он доступен;
2. по совместимому типу, номеру, точной дате и времени и логическому складу;
3. для реализаций — по уникальному совпадению даты, состава товаров и количества.

Товарные строки внутри одного документа агрегируются по коду номенклатуры, артикулу
или названию. Сопоставленные документы сравниваются только по количеству движения.
Расхождения стоимости игнорируются. Неоднозначные соответствия не выбираются автоматически.

Перемещения и передачи филиалу между физическими складами с одним готовым
`warehouse_mapping_id` считаются внутренними и исключаются. Между разными логическими
складами они остаются в сверке независимо от флагов учёта. Если выгрузка не заполняет
`СкладОтправитель` и `СкладПолучатель`, внутренняя передача определяется по двум сторонам
одного документа внутри готовой логической группы: должны присутствовать разные
физические склады, а движение количества каждого товара должно взаимно погашаться.

## 6. Сверка остатков

Остатки сравниваются отдельно для каждой бухгалтерской базы. Единицей результата
является комбинация:

- бухгалтерская база;
- логический склад;
- номенклатура;
- контрольная дата.

Начальный остаток относится к `start_date`, конечный — к `end_date`. В результат
включаются только несовпавшие остатки с учётом настроенного допуска количества.
БУХ2019 и БУХ2026 всегда представлены отдельными строками.

Если товар присутствует только с одной стороны, отсутствующая сторона получает нулевое
количество. Причина указывается явно: `Нет остатка в УТ` или `Нет остатка в БУХ`.
Код, артикул и наименование берутся с доступной стороны и не должны теряться. Стоимость
и суммы не сравниваются и не используются как основание для ошибки.

Разница количества рассчитывается как:

```text
БУХ − УТ
```

## 7. Состав XLSX

`POST /reconcile` возвращает один файл со следующими листами в указанном порядке:

1. `Итоги`;
2. `Расхождения остатков`;
3. `Довнести в БУХ`;
4. `Лишние в БУХ`;
5. `Проверить вручную`;
6. `Базы не проверены` — только при наличии ошибок источников.

### 7.1. Лист «Итоги»

Лист содержит количество прямых действий, ручных проверок, проверенных и непроверенных
баз, общее количество расхождений остатков и статистику отдельно по каждой БУХ.
В статистике каждой базы указывается отдельное число строк листа `Расхождения остатков`,
число исключённых документов и число документов, ожидающих правила типа.

### 7.2. Лист «Расхождения остатков»

Одна строка содержит:

- дату расхождения;
- артикул и наименование;
- остаток в УТ, остаток в конкретной БУХ/НБ и разницу;
- базу и тип остатка;
- причину;
- логический склад и код номенклатуры;
- склад УТ и склад БУХ/НБ.

Совпавшие остатки на лист не выводятся. Заголовок закрепляется, на таблицу
устанавливается автофильтр, для всех колонок задаются читаемые ширины.

### 7.3. Листы действий

- `Довнести в БУХ` содержит документы УТ, отсутствующие в конкретной БУХ.
- `Лишние в БУХ` содержит лишние документы и дубли БУХ.
- `Проверить вручную` содержит неоднозначные соответствия и допустимые документы,
  которые могут создаваться только в БУХ.
- `Базы не проверены` объясняет технические ошибки источников и способ повторной проверки.

Добавление остатков не изменяет состав и группировку существующих списков действий.
Сервис формирует рекомендации, но не изменяет данные 1С.

## 8. Проверка при приёмке

- В каждой строке расхождения есть артикул и наименование, в том числе при отсутствии
  товара в одной из баз.
- Видны значения УТ, выбранной БУХ и рассчитанная разница.
- БУХ2019 и БУХ2026 не объединяются.
- Начальный и конечный остатки используют соответствующие контрольные даты.
- Совпавшие остатки отсутствуют на новом листе.
- Расхождение только в сумме отсутствует во всех пользовательских листах.
- `Поступление дополнительных расходов` и `Заказ покупателя` отсутствуют в действиях.
- Документ подтверждённого типа проверяется даже без флагов БУ/НУ.
- Передача внутри одного логического склада отсутствует в действиях.
- Передача между разными логическими складами проверяется.
- Имя файла содержит обе даты периода.
- XLSX открывается как корректный ZIP/XML-документ; заголовки закреплены, фильтры и
  ширины колонок настроены.
- Полный набор unit- и contract-тестов проходит успешно.
